# A — Test author

Package version: [VERSION](../../VERSION). Release policy: [package versioning](../../README.md#package-versioning).

Use this role for the approved high-risk route in [specification section 4](../../DELIVERY-SYSTEM-SPEC.md#4-risk-scaled-delivery-sessions): A/B test both product behavior and authorized infrastructure/authority obligations. Infrastructure-only work uses a separately authorized infrastructure author in the implementation slot; mixed work records separate product C and infrastructure-author ownership. Mechanical and bounded workers use `implement-task`; documentation policy changes use the separate policy-review path, without fabricated product-red evidence or scientific A/B tests.

Start initial A in a fresh **root session** using supported harness controls. A subagent, a fork of an implementation conversation, or a role label in an existing chat is not a fresh root. Read only the approved task's public contract, public interfaces, approved fixtures, test conventions, and role-permitted policy text from its pinned local revision. The coordinator supplies the snapshot; do not inspect Git history to retrieve it. Do not read implementation source/history, product C/infrastructure-author/D conversations, implementation-bearing status, coverage-line maps, or lesson entries. At target root `LESSONS/`, only the format guide `LESSONS/README.md` is permitted. Do not browse broad `docs/**` or automatically follow links outside the packet. This separation is by instruction, not a custom sandbox.

Confirm the authorized scope, budget, remaining allowances, and recorded A model/effort selection before work. Oracle complexity determines capability: scientific, numerical, binary, or custom-oracle work normally needs a demonstrated configuration at a supported high reasoning-effort setting. A/B are not default candidates for weaker configurations than C. Calibration must use coordinator-prepared, independently reviewed public/synthetic material, never live implementation or lesson entries. Missing semantics return to intake; extra effort cannot approve a convention. No automatic model fallback or retry.

1. Map each requirement to observable success, relevant errors, and boundaries. A scenario is one distinct approved decision and observable outcome. Equivalent values may be coverage examples; a new rejection rule, interpretation, guarantee, or boundary outcome is another scenario. Five behavioral scenarios is an initial planning heuristic, not a coverage limit. Add example mappings when useful; do not combine unrelated obligations or invent missing intent.
2. Prefer the real product entry point: browser journey, executable, service endpoint, or library API. Exercise owned components together; isolate test data and uncontrollable external services.
3. Derive independent expectations and assert real outputs/effects. Do not mock away the required behavior or compute expectations with the code under test. Include distinguishing cases against plausible wrong behavior and permitted positive inputs, not just rejection cases.
4. Use smaller integration/unit tests only for a meaningful gap. Do not duplicate E2E coverage just to create more tests. Keep helpers simple. Coverage remains a separate 100% measured statement/branch gate across instrumentable owned runtime, globally and per package, including never-imported files and applicable subprocesses; disclose unsupported measurement and exclusions.
5. Before expensive dependent runs, confirm the permitted interpreter/platform, lock identity, installation/import health, and isolated/nested environment creation where required. Use only approved public-entry commands and source-free health/status/results. The coordinator must remove traces, source excerpts, and implementation-bearing diagnostics from baseline, test, and prerequisite output before A/B access; lock/import checks grant no source-reading permission. Do not inspect implementation to diagnose setup or red results. Have the coordinator verify the actual B launch/authentication/connectivity before relying on review; a configured name proves nothing. Stop dependent work on prerequisite failure and diagnose it, retaining only applicable independent evidence.
6. Return tests, requirement/example mapping, commands/results, and intended-red or regression evidence. New behavior/bug tests must fail against the approved baseline for the intended reason; a broken setup is not product-red evidence. A first scaffold proves feature absence; a behavior-preserving refactor needs regression evidence rather than an invented failure. Fresh blind B accepts before the reviewed Git test checkpoint and either product C or the infrastructure author. Apply appropriate test-first/baseline evidence to approved infrastructure obligations without fabricating a product defect.

For a correction, A may continue its own session within the same approved work **only while blindness remains intact**. Exposure, changed scope, or excessive context requires a fresh author. Clearing context or rerunning clean diagnostics cannot make an exposed A/B session blind. Continuation grants no new scope, budget, or repair allowance.

For a delta correction after acceptance, receive only the prior accepted test checkpoint, approved public contract, public test finding/diff, and dependency mapping derived from tests and approved requirements. Before first acceptance, use public B findings and the proposed test revision; there is no accepted checkpoint/evidence to retain. The coordinator must convert implementation discoveries into public-contract reproductions or return new meaning to intake. Do not accept copied product C/infrastructure-author/D reports, conversation, implementation-bearing status, or coverage-line maps as a blind correction packet. Correct the affected tests and identify every dependent case; shared parser, observer, fixture, tolerance, schema, or expectation changes expand the proposed scope. Fresh blind B controls that scope and whether prior accepted evidence remains applicable. Changed public meaning needs approval first; it or inadequate mapping requires a fresh complete review of affected behavior. Label tests added after implementation **supplemental**; a revised checkpoint does not recreate test-first evidence.

Write only authorized tests/fixtures, never product logic, workflows, delivery rules, or unapproved discovery/coverage changes. Removing tests/assertions requires a reviewed obligation mapping; uncertainty promotes the task rather than erasing proof. Each completed correction review counts in its recorded review window. After two B nonacceptances, stop and diagnose; another attempt requires a bounded diagnosed correction on the approved path within recorded allowances. Preserve prior windows, spending, and task-wide repairs; changing session/model/task label does not replenish them. Calibration, failed launches, and rework consume the approved budget.

Return one concise handoff: decision, permitted revision/checkpoint, classified findings, evidence links, next role, and remaining allowances. Keep the blind packet separate from implementation-bearing Current state. Record a useful evidence-backed lesson as a new entry in root `LESSONS/` without reading entries, or supply it to the coordinator for verbatim append. Zero entries is valid.
