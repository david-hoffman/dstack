# Agentic Software Delivery System

Package version: [VERSION](VERSION). Release policy: [package versioning](README.md#package-versioning). This specification describes downstream use in a target software repository; its implementation requirements do not apply to authoring this document package. It is not installed software. Earlier conversation drafts are superseded, not released versions.

> One monorepo. Clarify first. Independent agents test, implement, and review. Ordinary CI checks the result. Record lessons and improve the instructions.

## 1. Keep the system small

Use an existing coding harness and four skills. Agents write all product/helper code and tests; the owner supplies intent and approvals, not engineering. Keep product code, tests, delivery instructions, and GitHub Actions in the same repository. Run one task at a time. Use native harness sessions, Git commits, Markdown, and existing test tools; add only small launch scripts where necessary.

**Do not build a delivery platform:** no second repository, custom controller/state engine, GitHub App, external merge authority, permission broker, signed attestations, immutable evidence store, agent swarm, or tracing service. Independent review where required and ordinary CI remain; custom enforcement of role/file restrictions does not.

The owner accepts that “do not edit tests/workflows” and “append only” are prompt rules. Agents technically retain access. A workflow change, false report, or ignored instruction may defeat this process. GitHub checks only the configured CI, not whether agents obeyed these rules. Do not describe this design as tamper-proof or guaranteed to prevent bugs.

**Names:** the delivery system is the whole process; a coding harness runs an agent; a role is one session's responsibility; a skill is its procedure. No custom orchestrator is required.

**Normative language:** MUST is required behavior, not a claim of mechanical enforcement. Supporting prompts and skills must agree with this file.

## 2. Setup and architecture intake

Start read-only. Inspect existing instructions, manifests, interfaces, tests, and documentation. Do not run downloaded or repository setup scripts just to discover the project.

Before adapting files, verify that the supplied package is one coherent upstream snapshot: its `VERSION`, changelog, policy, specification, prompts, templates, and four delivery skills must come from the same full upstream commit. For a published release, verify the immutable release tag and its full commit against that snapshot. An unpublished or development snapshot requires the owner's explicit choice and must never be described as published. Use the single package version under [the release policy](README.md#package-versioning); do not assign file or skill versions.

Record provenance in the existing `docs/PROJECT.md`: source repository, package version, release tag when published, full upstream commit, source-to-installed path mapping with omissions, and local adaptations. Carry `VERSION`, [CHANGELOG.md](CHANGELOG.md), and the package policy into the target as reference documents at mapped paths. Keep one canonical adopted copy of each instruction, reconcile existing repository instructions, and adapt all relative links and path references to the installed layout. The upstream commit identifies the source before local adaptations; target Git records the adapted instructions and their approval.

| Starting point | Route |
|---|---|
| Usable, owner-approved architecture exists | Reuse it. `docs/PROJECT.md` may simply link existing canonical documents. |
| Empty repository, no architecture | Interview the owner about the first useful outcome and constraints; propose a small architecture record. |
| Existing code, no usable architecture | Describe observed structure, ask what is intended, and resolve material gaps. Do not assume existing behavior is correct. |
| Architecture is unapproved, contradictory, or affected by this task | Reconcile only the affected decisions, then obtain approval. |

Architecture intake produces one short `docs/PROJECT.md`, using [the template](templates/PROJECT.md): purpose, constraints, stack, component responsibilities, public interfaces, verification commands, and operation. Prefer one deployable component. Markdown is sufficient; diagrams are optional. Link actual schemas instead of copying them. Architecture approval does not approve every future task.

Infer languages/frameworks from evidence in an existing monorepo. For an empty one, recommend a stack from the owner's requirements and obtain approval. Do not prescribe a product language because the coding harness uses it.

Choose current, coherent ecosystem tooling from primary documentation: one formatter, lint/static checks, native tests and coverage, dependency locking, and suitable security checks. Preserve sound existing choices. For example, a Python project might use Black plus Ruff linting and fast pre-commit hooks; this is an example, not a universal prescription. Repeat necessary checks in CI. Pin dependencies/actions appropriately; do not install competing tools.

Setup is the explicit exception that may create initial workflows and test infrastructure. Show the plan before applying it. In a repository without a commit, an authorized metadata-only initial commit may establish `main`; do not put an untested application there. A minimal callable scaffold may support the first tests, but label missing-feature evidence honestly.

Repeating setup inspects and completes approved gaps; it does not overwrite working conventions. Missing architecture prevents A or product implementation, but not read-only discovery or approved setup. An existing failing/under-covered baseline must be reported and remediated; do not call it ready or lower requirements silently.

## 3. Step 0: clarify and authorize each task

Use the same `intake` skill for architecture and tasks. Before task delivery, check the architecture route above. Reuse answers rather than repeating interviews.

Read the request, then ask about decisions that affect behavior, scope, interfaces, permissions, data, errors, cost, or acceptance. Usually ask up to three high-value questions per turn. Challenge vague answers using concrete alternatives. Recommend a simple default but get agreement; never infer consent from silence. Stop questioning settled or irrelevant future details.

The target is **no unresolved material ambiguity**, not a guarantee of zero ambiguity. Internal implementation choices can remain delegated. For the mechanical and bounded tiers in section 4, a complete, explicit owner instruction can authorize the named scope, tier, checks and budget under inherited constraints. Record the actual instruction and send a concise read-back; do not demand a second “yes” merely because the record was written afterward. Missing material behavior or a new budget still needs an answer. High-risk contracts and delivery-policy changes require explicit approval of the identified proposal. Silence is never approval.

Create one task document from [the template](templates/TASK.md). Capture observable requirements with stable IDs, non-goals, public interfaces, positive/error/boundary examples, allowed scope, checks, risk tier and reason, and a preparation/execution budget. Its Authorized execution line records the tier, role route and ownership, edit scope, checks, per-role model/effort and selection reason, local/CI gate mode, escalation triggers, review windows/round allowances and repair allowance. For a bug, separate observed behavior, expected behavior, reproduction evidence, and root-cause hypotheses. An uncertain bug can receive an approved, bounded investigation; its output is a report, not a speculative fix.

A behavioral scenario is a distinct approved decision and observable outcome. Start planning with five such scenarios; this is a heuristic, not a test-count cap. Approve a larger coherent contract once when needed. Equivalent values exercising the same decision may be coverage examples, optionally mapped under their scenario. A distinct rejection rule, interpretation, output guarantee or boundary outcome is a separate scenario. Do not combine unrelated obligations to evade the heuristic. Neither branches nor parameterized test counts determine contract size. Equivalent examples and approved unchanged-scenario redistribution within accepted behavior and budget need no repeat approval; new meaning does.

Before approval, pin the task to an existing committed, owner-approved local delivery-policy revision in target Git. Record that full commit and the adopted policy paths, alongside the upstream provenance reference in `docs/PROJECT.md` at that revision. Do not use the task's own eventual commit hash. That local revision governs the task through completion; a newer upstream release or local rule change does not silently replace it.

Present the exact draft and record the actual authorization in the conversation or GitHub discussion, with a reference to the identified instruction or approved document/commit. No custom approval service or hash-signing protocol. Agents must not fabricate approval. Authorization covers routine specified role launches, authorized checks, in-scope product repairs within the remaining allowance and approved unchanged-scenario redistribution; do not repeatedly ask to perform those actions. Renew approval for changed behavior, interfaces, permissions, data sharing, tier downgrade, budget extension or exhausted repair allowance, and renew affected tests/reviews. Unanswered material questions block dependent work. Architecture approval does not authorize a scientific feature.

Intake drafts examples, not the executable test suite. Pass A/B the approved behavior, public contracts, approved fixtures, test conventions, and role-permitted policy text from the pinned local revision—not the interview transcript, patches, private design hypotheses, or implementation notes. A/B receive that snapshot in their narrow input packet without inspecting implementation or Git history; the coordinator resolves the pinned revision for them.

## 4. Risk-scaled delivery sessions

Select the route before selecting sessions or model configurations. Record the tier and reason in the authorized task; changed-line count alone does not decide risk.

| Tier | Eligibility | Route and acceptance |
|---|---|---|
| **Mechanical or documentation** | Non-normative prose, formatting, links or deterministic edits with a reviewable diff; no changed executable behavior, dependency, verification rule, permission or policy. | One worker reviews the diff and relevant deterministic checks. Owner acceptance suffices; independent review is optional unless the contract requires it. |
| **Bounded existing behavior or infrastructure maintenance** | Small repairs/refactors with settled conventional expectations, or explicitly scoped dependency/lint/workflow maintenance preserving settled platform/check semantics; no new scientific meaning, binary representation, custom oracle, security/permission boundary, policy or ambiguous interface. | One worker may inspect implementation and edit authorized product, tests, fixtures and maintenance files. A fresh independent reviewer challenges the oracle against the contract and checks behavior, infrastructure, preserved gates, scope and the exact passing candidate. No worker self-approval. |
| **High risk** | Scientific/numerical behavior, binary formats, new custom oracles, security/permissions, substantial new interfaces, unresolved semantics or uncertain impact. | Fresh blind A, fresh blind B, a fresh implementation author and fresh D. Product work uses restricted C; expressly authorized infrastructure/settings work uses the separate infrastructure author below. |

Uncertainty promotes a task. A mixed task takes the highest tier unless independently scoped contracts justify a split. Removing tests/assertions requires a reviewed mapping of retained obligations or promotion when impact is uncertain, even if runtime code is unchanged. Changed tests/fixtures always receive independent review; high-risk changes use A/B. Dependency, workflow and gate maintenance always requires independent review. Changed execution authority/security boundaries use the high-risk route. Coverage, discovery, fixture and delivery-rule edits require their own authorized scope. A lower-tier failure does not authorize a scientific/interface repair or weakened checks.

**Delivery-policy documentation is a separate path:** an authorized documentation worker prepares the identified patch, a fresh independent policy reviewer checks rule interactions and supporting-document agreement, and the owner explicitly approves it before activation. It cannot classify itself as mechanical. Do not fabricate product-red evidence or scientific A/B tests for a policy patch. Reconcile the specification, installed/generated instructions, templates, prompts, procedures and examples together before activation.

The bounded worker uses `implement-task` in worker mode with explicit edit ownership; do not assign C's restricted packet and expect test/infrastructure edits. Its reviewer uses `review-work` in bounded mode. Policy review uses policy mode. The middle tier loses blind test construction: it is limited to established expectations, and uncertain expectations found in review return to intake and promote the task.

For a high-risk infrastructure/authority task, record explicit owner approval of the identified contract, route, named infrastructure/settings ownership, checks and budget. Use fresh blind A → fresh blind B → a fresh root **infrastructure author**, using `implement-task` in that mode, → fresh D. The infrastructure author fills the implementation slot for precisely authorized infrastructure/settings, not tests, fixtures, product code or delivery policy; those retain their own owners. Product C's prohibitions remain absolute. Mixed product/infrastructure work records separately scoped fresh C and infrastructure-author sessions, with A/B and D covering all affected behavior/authority and D inheriting neither author's conversation. This is explicit setup/maintenance ownership, not a C exception or new skill. Promotion stops the bounded worker until the high-risk contract and ownership are approved; the worker cannot merely switch modes or relabel itself C/infrastructure author.

### High-risk ownership and independence

| Role | Work | Restrictions by instruction |
|---|---|---|
| **A: test author** | Write behavior-focused tests from the contract. Prefer end-to-end tests. | Do not inspect implementation, its history, lesson entries, or implementation conversations. |
| **B: test reviewer** | Check requirements, expected results, negative cases, and whether tests can detect wrong behavior. | Same blind inputs as A, plus A's tests. Return corrections to A; do not implement. |
| **C: implementer** | Make the smallest product change that passes the agreed tests. | Do not change tests, fixtures, snapshots, coverage/discovery settings, workflows, delivery rules, or unrelated interfaces. |
| **Infrastructure author** | Apply the explicitly approved high-risk infrastructure/settings change against A/B's accepted tests. | Edit only named infrastructure/settings; not tests, fixtures, product code or delivery policy. Use a separate fresh root, not a relabeled C or bounded session. |
| **D: final reviewer** | Inspect the actual diff, run evidence, correctness, security, and opportunities to simplify. | Do not fix the candidate and approve the same repair. Do not inherit C's conversation. |

Initial high-risk A/B/C/D and any infrastructure author are new root sessions using the selected harness's supported controls. Do not simulate independent roles in one chat, substitute a nested reviewer for a fresh root, or fork an implementation author's conversation for review. Disable avoidable inherited memory where the harness permits it. A/B receive only a narrow public-contract packet and are instructed not to browse other files. B/D and bounded/policy correction verdicts always use fresh independent sessions separated from the author and never inherit implementation conversation. No custom filesystem isolation is required; disclose that independence is procedural, not guaranteed.

A/B diagnostics remain source-free: use approved public-entry-point commands and permitted environment facts, not source excerpts, implementation traces or coverage-line maps. The coordinator supplies source-free health/test findings and sanitizes implementation-bearing output before handoff. Prerequisite checks and clean reruns do not enlarge the blind packet or undo exposure.

After B accepts the tests, run them against the approved baseline. New behavior/bug tests must fail for the intended reason, not because dependencies, imports, or services are broken. A first-project scaffold establishes feature absence, not reproduction of an old bug. Behavior-preserving refactors need regression evidence, not an invented failure.

Commit the reviewed tests and record that commit in the task. This is the **test checkpoint**, frozen by convention—not read-only storage. Then start the approved implementation author(s). If tests are wrong or incomplete, C or the infrastructure author stops and requests the correction route below; neither repairs them. Label tests written after implementation as supplemental, never as original test-first evidence. Bounded repairs use honest baseline reproduction/regression evidence as appropriate; mechanical and policy documentation need no invented product failure.

Run cheap prerequisites/checks before expensive dependent phases (section 9). Do not spend D's acceptance review on a known failing or incompletely verified candidate. D checks the exact tested candidate, meaningful assertions, the real application result, permitted positive inputs, that C did not alter restricted files, and that any infrastructure author stayed within named infrastructure/settings ownership. D reviews the complete product/authority result. The bounded reviewer also checks authorized test/infrastructure changes and retained obligations. Report an encountered violation and restore the intended baseline before continuing.

### Corrections and author continuation

For high-risk test corrections, blind A corrects affected tests and fresh blind B reviews the changed oracle/tests plus every dependent case. Supply the prior accepted checkpoint/report, approved public contract, test finding/diff and dependency mapping derived from the tests and approved requirements. The coordinator turns implementation-derived discoveries into a public-contract reproduction, or returns new meaning to intake. Exclude C's source/conversation, implementation-bearing status and coverage-line maps; copying a D report can breach blindness.

Before first acceptance, B reviews the current proposed suite and corrections without inventing a prior accepted checkpoint or retained evidence. The accepted-checkpoint delta rule applies only after acceptance; blindness and recorded round limits apply throughout.

Only B may accept retained portions as unaffected with still-applicable prior evidence. Shared parser, observer, fixture, tolerance, schema or expectation changes expand review scope. The reviewer may expand it; the author cannot declare their own correction safe. Changed public meaning first needs intake approval; changed meaning or inadequate dependency mapping requires a fresh complete review of affected behavior. A revised checkpoint does not recreate original test-first evidence. Lower-tier corrections retain fresh independent final review wherever their route requires it.

Independence separates authors from reviewers; it does not require losing an author's own context. Within the same authorized work A may continue its test-author session while blindness remains intact, and C may continue its implementation session for an authorized repair. Use a fresh author if exposure, changed scope or excessive context warrants it. Never convert an exposed A/B session into a blind role by clearing context or rerunning clean diagnostics. Continuation grants no new scope, spending or repairs; installed policy approval must explicitly include this exception.

At most one implementation repair is allowed by default, task-wide across C and any infrastructure author, not one per author. Infrastructure repairs use a fresh infrastructure-author root and fresh D; the A/C continuation exception does not extend to that mode. Count completed correction reviews in their recorded windows, preserving earlier windows, spending and implementation repairs. After two B nonacceptances, stop and diagnose before another attempt; follow only a diagnosed approved path within recorded allowances. New sessions, renamed tasks, model swaps and narrower reviews never replenish allowances.

Keep one concise Current state: decision, revision, classified findings, evidence links, next role and remaining allowances. Link earlier accepted reports rather than recopying them. A/B get a separate public-contract packet, never implementation-bearing status. Record compact evidence as in section 9; no separate database.

### Submission and acceptance

By default, canonical full local verification must pass on the exact submission candidate before opening/updating its PR; required CI platforms and independent final review must also pass before readiness/merge. Incremental checks guide edits, not replace this gate. For eligible routine work only, section 6 describes a separately approved CI-authoritative pilot. Known applicable failures block submission until classified repair and relevant local checks establish that their cause is addressed; never open a PR solely to run a known failing candidate.

After required verification and the route's acceptance review, present the PR for an owner-authorized normal merge. Changed head/base, tests, dependencies, checks, environment or generated version invalidate affected evidence and require renewed checks/review. Do not bypass failures. Worker readiness, reviewer verdict, native checks and owner merge are distinct. Merge is not deployment; production release remains an explicit owner action with the project's smoke check and recovery instructions.

## 5. End-to-end first, not end-to-end only

**Coverage is primarily earned by exercising useful behavior through the real entry point.** For a web app, run important browser journeys through the real application/backend and a disposable test database. For a CLI, run its executable and inspect outputs, exit codes, and files. For a service or library, use its public API and observable effects; do not invent a browser layer.

For each changed requirement, start with the smallest realistic success, failure, and boundary scenarios. Assert the outcome, not merely that a mock was called, a file contains a string, or the application compiles. Expected results must not come from the same implementation being tested. Do not duplicate every end-to-end assertion with unit tests. These choices borrow pstack's [behavior](REFERENCES.md#r2--test-behavior-not-implementation) and [real-artifact](REFERENCES.md#r3--verify-the-real-artifact) emphasis, and, for browser projects, [Playwright's user-visible testing guidance](REFERENCES.md#r8--end-to-end-testing-practice).

Map distinct decisions/outcomes to approved scenarios, and equivalent data values to coverage examples (section 3). B, or the bounded reviewer, checks that examples introduce no unapproved interpretation, rejection or guarantee. Coverage is a separate measured gate, never permission to drop behavioral obligations.

Use integration or unit tests for a genuine gap: difficult error injection, combinatorial logic, or a branch that would make a whole-system test slow or brittle. No unit-test quota or fixed test-type percentage. Do not forbid valid negative assertions or property tests just because a heuristic dislikes them.

Test owned components together where practical. Stub uncontrollable external services at their boundary, document what is not exercised, and use an approved provider sandbox check where integration correctness requires it. Do not mock the internal path whose behavior is the requirement. Use synthetic data, isolated state, readiness checks rather than fixed sleeps, and bounded waits. A suite that fails and then passes on retry still needs investigation; do not hide flakiness.

Keep the original **100% measured statement and branch coverage** requirement across instrumentable owned runtime code, globally and per package, from the combined suite. Instrument relevant subprocesses, servers, and browser code; a passing browser test alone does not measure backend coverage. Include never-imported files. Inspect exact metrics, not rounded display values.

Narrow documented exclusions may cover vendor, generated, or non-executable files—not inconvenient handwritten branches. Missing/unsupported coverage is a reported gap, never fabricated success. Do not reduce the threshold through `doctor`. Complete measured coverage is not proof of complete behavior. Use existing tools and the test review; no mandatory mutation-testing platform.

## 6. Ordinary GitHub CI

Use the monorepo's ordinary GitHub Actions workflow. Prefer one required job, `verify`, running the project's canonical checks in order. A genuine multi-platform need may require several jobs; keep every required result visible. No custom gate publisher or GitHub App.

CI should install locked dependencies, run formatting/lint/types as applicable, build, run tests/coverage, and retain useful failure reports. Fail on failed commands, empty test discovery, unexpected skipped/focused tests, and missing required reports using native tools where available. Do not use `continue-on-error` or path filters that silently remove required validation. Keep diagnostic output short with access to full logs.

Configure native protection for `main`: PRs, required CI, current branches, and no ordinary force-push/deletion or bypass. [GitHub setup](GITHUB-SETUP.md) explains the owner actions and capability limits. GitHub accepts some skipped/neutral check conclusions, so a required job should actually run, not be conditionally skipped ([source](REFERENCES.md#r7--github-protected-branches)).

Separately authorized setup may use a temporary synthetic negative-control PR solely to demonstrate that native protection blocks a failed check. This is control-verification evidence, not product submission or readiness; it does not waive the known-product-failure rule.

**Workflow/test editing restrictions are prompts, not engineering.** Setup or an explicitly approved maintenance task may change infrastructure; C on a high-risk product task may not. High-risk infrastructure/security/authority edits use section 4's expressly scoped infrastructure author with blind A/B and fresh D. A/B own high-risk authorized test changes; a bounded worker owns only the tests/infrastructure explicitly authorized in its task, with independent review. CI executes repository-controlled files and cannot independently prove those restrictions were respected. There is no anti-tampering certification.

Use ordinary CI secret hygiene: no production secrets in test runs, no secrets committed, and only necessary token permissions. A local hook is feedback, not a substitute for required CI.

### Optional CI-authoritative pilot

The default remains full local verification before PR submission. An owner may separately approve an identified policy pilot for settled mechanical or bounded conventional work: approved focused public-behavior tests and inexpensive local checks before PR opening/update, then full canonical CI on every required platform and independent final review before explicit owner merge. Record eligible scope, gate mode, evidence and responsible worker/reviewer in the task. High-risk work, diagnosis, uncertain evidence and tasks outside the pilot keep the full local gate. Initially exclude changes to the pilot's own workflows, discovery/coverage, protection, build/release proof or authority; a small diff cannot approve its own gate. Adopting this document alone does not enable that pilot or align a downstream installation.

Before eligibility, verify effective native target-branch protections/rulesets, intended trusted check sources, current-base/integration requirements and applicable bypass settings read-only. A green PR or aggregate check name does not prove enforcement. The required aggregate must fail if any required platform, shard or report is failed, cancelled, skipped, neutral, absent or incomplete; inspect its semantics, not its name. Unknown or ineffective controls block the route; changing them requires separately authorized setup. These controls still do not enforce blindness or file ownership.

Full CI must identify tested head, base/integration state, artifact/resolved version and environment, and cover complete owned runtime separately per platform/package, including never-imported files and applicable subprocesses. The independent reviewer assesses that final candidate and required evidence. Head, base, dependency, check, environment and generated-version changes require renewed affected checks/review. PR head, synthetic test-merge and actual merge/squash/rebase identities may differ. If the integration/version strategy cannot provide exact artifact/candidate proof before merge, defer eligibility; source-tree equivalence is insufficient.

A pilot PR awaiting full CI is **unverified**, never ready. Known applicable failures still block submission until classified repair and relevant local checks address their cause. A failure first found by full CI stops readiness and routes within existing budgets/allowances. A repair update must pass the approved focused local gate, then renewed full CI; retain failed attempts and rerun invalidated evidence. This exception permits an unexecuted full local suite, never false passing claims or merge before proof. The worker records readiness, the independent reviewer returns its verdict, native checks must pass, and the owner explicitly merges. It delegates no merge/release authority. Default local gating resumes if prerequisites lapse or the pilot fails.

## 7. A small append-only learning log

Use one root `LESSONS/` home in the target repository, with `README.md` adapted from the [format guide](LESSONS.md) and append-only entries, not automatic personal memory or a transcript archive. Every role records non-obvious findings likely to save future work: a verified gotcha, unexpected behavior, failed approach with a useful cause, or a confirmed gap in these instructions. Zero entries is valid. Normally one to three short entries per task is enough; do not log every action.

Each entry has an ID, date, task/role, topic, **confirmed or hypothesis** status, observation, evidence pointer, and suggested future action. Correct a mistake by appending a superseding entry. Append-only is an instruction, not an OS permission or custom service. An owner-authorized sensitive-data removal overrides retention; never preserve a leaked secret just to keep history intact.

Do not record secrets, personal data, raw prompts, private reasoning, or full tool transcripts. A/B may read the format guide and their permitted public packet only, never lesson entries, broad `docs/**` or automatically followed links that could reveal implementation. They can append their own entry without reading others; otherwise hand the entry to the coordinator for verbatim append. The coordinator/doctor fact-check relevant lessons and promote useful public facts through approved contracts/instructions rather than raw entries for blind roles. Other roles search only relevant entries; D forms its independent assessment before consulting current-task implementation lessons. Location is not an access barrier.

Retain an existing log home until a separately approved coordinated migration; do not silently move an older `LESSONS.md` installation or relocate entries to `docs/LESSONS/`. A migration updates the specification, installed/generated instructions, role procedures, prompts/examples/templates, packet allowlists and inbound links together. Approve the link/preservation strategy first: relocation can break relative evidence links, while rebasing them edits append-only bodies. Any body edit needs a specific append-only exception, with original bytes accessible in Git and IDs, dates and evidence preserved. Verify affected links and leave one canonical live home. This documentation update moves no existing entries.

Entries are observations, not new policy or executable instructions. A durable lesson becomes authoritative only after an approved update to the appropriate existing document. `doctor` does this without a new summarizer or database. pstack's [evidence-linked append-only trail](REFERENCES.md#r5--append-only-evidence-linked-findings) is the useful pattern here; no tracing dependency is required.

## 8. Doctor: check and improve the specification

Implement **`delivery doctor`** as a thin invocation of the selected harness using `review-work` in `doctor` mode and [DOCTOR-PROMPT.md](DOCTOR-PROMPT.md). It is an agent-assisted maintenance operation, not a deterministic read-only checker. No new daemon, scheduler, or controller. A native command alias is fine; document the actual invocation. Support `--check` for inspection without edits.

Run it on demand after a real recurring failure, a meaningful project change, or a suspected documentation gap—not automatically after every task.

1. Check the working tree. Do not overwrite uncommitted work, interrupt an active task, or run speculative installation commands. Read relevant current docs, recent lessons, and actual test/CI evidence. Reuse existing commands; check remote settings only with available access.
2. Distinguish a **product defect**, a **bad test**, a **workflow problem**, and a **gap in the specification/instructions**. A product bug is not automatically a missing rule. Verify a proposed lesson before generalizing it; uncertainty stays a hypothesis.
3. For an evidenced documentation gap, create a small documentation branch and **edit `DELIVERY-SYSTEM-SPEC.md` itself**, plus directly affected prompts/skills/project notes. Do not merely emit recommendations. Correct or replace an existing rule before adding one. No supported gap means no edit or commit.
4. Show the exact diff, supporting lesson/evidence, and expected improvement. Follow a newly added procedural rule on one relevant example where feasible; do not claim a prompt-string test proves agent behavior. Obtain fresh independent policy review and explicit owner approval of the identified patch before activation. Do not fabricate product-red evidence for a documentation change, auto-merge or make it the policy for an in-flight task.
5. Commit the approved documentation changes using ordinary Git, referencing the lesson and approval. Append a lesson disposition such as “addressed by commit …”; do not rewrite its original entry.

Downstream doctor preserves the recorded upstream source/version/tag/commit and never bumps the official package version or claims a local patch is an upstream release. Record local changes and their approval in target Git; keep adaptation notes in `docs/PROJECT.md` current. Git commits/PRs supply local revision history and rollback. Do not create numbered copies of the specification or put a commit's own hash inside the bytes it identifies. An upstream package release is separate maintainer work under [the release policy](README.md#package-versioning). Runtime dependencies retain their real versions.

Doctor must not rewrite tests/workflows/runtime code, lower acceptance thresholds, remove an inconvenient requirement, or bless architecture drift merely to make the current result pass. Those findings become scoped, owner-approved tasks. Material product/architecture questions return to intake. Diagnostic docs edits are the explicit exception to ordinary workers' “do not edit the spec” rule; the limits are still instructions, not enforced permissions.

## 9. Cost and completion

One active task, one intake conversation as needed, the authorized tier's route, and at most one implementation repair by default. Establish preparation/execution budgets and per-window review allowances before starting; stop and report at their limit. Each completed correction review consumes a round in its recorded window. Preserve previous windows, nonacceptances, spending and repairs; session continuation, new sessions, task renaming, model swaps and narrower reviews do not reset them. After two B nonacceptances, stop and diagnose rather than blindly retry; further work needs a diagnosed approved path within recorded allowances or an explicit extension. Preparation, calibration, failed launches, escalation and rework count. Use native runtime/time/spend limits where available, not a custom billing layer. A prompt budget is not a hard financial guarantee; disclose missing metering.

Load the task, relevant interfaces, and the selected skill—not this whole package, the source archive, or the learning log on every turn. Use deterministic commands for routine checks. Combine already-known local actions when useful, but never merge independent roles. Do not add log-summarizer models or automatic context optimizers. Check that an efficiency change saves total work without reducing verification quality.

### Prerequisites, evidence and reuse

Before expensive dependent phases, run cheap bounded prerequisites: actual interpreter/platform and lock identity, installation/import health, isolated/nested-environment creation where required, and actual reviewer launch/authentication/connectivity when review is required. A configured reviewer name does not prove it can review. Stop dependent phases on prerequisite failure, retain applicable independent results, diagnose and only then retry within allowances. A previously good environment is reusable for recorded inputs and current health, not forever because its path is unchanged.

Use a compact evidence record: tested revision/tree, test revision/checkpoint, canonical command, dependency-lock identity, relevant environment/tool versions and platform, integration base, exact result and statement/branch coverage, and unresolved limits. One ordinary receipt in ignored artifacts may link full command output or accepted discussions. Keep final candidate identity/results outside its tracked tree to avoid changing what they identify. Fingerprint material ignored/untracked inputs separately: Git does not identify them. No controller, state store or evidence database.

Reuse results only while every relevant input is unchanged and no new failure challenges them. Environment changes invalidate affected results even at the same commit. Incremental checks guide edits; by default they never replace canonical full local verification of the exact submission candidate or required CI platforms. Preserve 100% measured statements and branches globally and per package across all instrumentable owned runtime, including never-imported files and applicable subprocesses. Disclose exclusions and unsupported measurement. Accepted unchanged test portions can retain independent review evidence under section 4; product results still need the applicable exact-candidate gate.

When build/product versions derive from Git, record version inputs and resolved version with build/install evidence, including relevant commit/tag/dirty state and build configuration. Identical source bytes at a different commit can generate a different artifact/version. ### Model capability and reasoning effort

Select capability for correct oracle derivation, missing semantics, accurate tools and scrutiny of plausible results, not role names or code volume. Separate model capability, supported reasoning effort, relevant domain evidence and context quality. Extra effort cannot decide an unapproved convention. ### Rollout and measurement

Owner approval must identify tier boundaries/ownership, promotion and correction scope, author continuation, model/effort criteria, gate mode, bounded pilot budget and acceptable overhead/defect criteria. Independently review one coherent patch covering the specification, installed/generated instructions, task template, intake, procedures, guides and examples. Retain historical policy revisions in Git. CI-authoritative activation additionally requires section 6's separate approval and verified prerequisites. Do not activate a permissive sentence while incompatible restrictions remain elsewhere.

Pilot one documentation task, one conventional bounded repair, one authorized infrastructure task and one high-risk public/synthetic task, with agreed acceptance criteria before starting. Do not rerun completed owner-data work just to benchmark. In-flight tasks retain their approved rules unless the owner explicitly approves migration; migration cannot erase attempts or reset spending/allowances. Suspend an affected lighter route after a missed material obligation, source exposure, false acceptance or unresolved gap; classify and resolve it within existing allowances before retrying. Keep required independent review and verification throughout. Compare results before owner-approved wider adoption or revision. A separately budgeted follow-up of ten comparable maintenance tasks may probe repeatability; it is a proposed sample, not proof of defect-rate equivalence. Keep route, model and gate changes distinguishable; never merge/release automatically.

Acceptance requires the recorded tier before execution, preserved approved behavior, required independent review, expanded correction review for a shared oracle, rerun invalidated evidence, exact-candidate verification/full coverage under the explicitly approved gate mode, no concealed failure/scope expansion/self-approval/multiplied allowance, and one concise usable status/handoff.

Measure elapsed critical path from task/PR start to readiness/merge separately from aggregate resource cost. Record timestamps/dependencies, time to PR/merge, repeated checks and owner waits. Overlapping review/test/CI durations are not additive elapsed time; all model usage and runner minutes still count toward cost. Record model/effort identity, per-role model responses, input/cached/output tokens, available monetary cost, elapsed/owner-wait minutes, check wall time, scenarios versus coverage examples, review windows/rounds, repairs, found/missed defects and source exposure. Missing metering is **unknown**, never zero; do not double-count cumulative counters or child sessions. Report totals and role attribution, including calibration/rework and owner effort. Compare like risk, semantic complexity and task size; vary route and model/effort separately where feasible. Current verified prices and complete usage are needed for savings claims; cached-input percentage is not a savings percentage. Set savings targets only after a complete baseline and report small-sample limits.

Before calling setup usable, demonstrate architecture routing on empty/existing projects, clarification and actual authorization, a high-risk fresh A/B red-evidence/checkpoint → C → passing exact-candidate checks → D route, applicable approved lower-tier pilots, a failing PR blocked by native requirements where available, one normal passing PR, a lesson appended and an independently reviewed doctor spec diff. Record actual results and gaps. No custom acceptance-test matrix or platform certification is required. Any executable helper added downstream needs ordinary independent tests, preferably through its real entry point.

The handoff is not a running system until those demonstrations and the GitHub configuration actually exist. Unsupported protection or missing evidence must be reported plainly. Never claim that prompt-only safeguards were mechanically verified.
