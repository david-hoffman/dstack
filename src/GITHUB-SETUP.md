# GitHub setup

Package version: [VERSION](VERSION). One monorepo, ordinary Actions, native branch protection. No external control repository, custom gate publisher, or GitHub App. These instructions are unapplied until authorized setup is completed and checked in the target software repository; authoring them activates no protection or CI-authoritative pilot.

## Implementer

Start read-only: identify the repository/target branch, existing CI, account capabilities, effective branch protections/rulesets, intended trusted check sources, current-base/integration requirements, and applicable bypass settings. Preserve useful workflows. Propose the minimal settings/infrastructure diff and scope/budget before applying it. Unknown access or protection gaps must be reported with exact remaining owner actions. Read-only inspection does not authorize settings changes.

Create/adapt ordinary canonical checks, preferably one required job such as `verify`; use the existing name instead of adding a duplicate workflow. For genuine platforms/shards, require every applicable result and complete report. The required aggregate must fail for any failed, cancelled, skipped, neutral, absent, or incomplete required platform/shard/report. Its own successful name alone is insufficient proof. Do not silently omit required targets with path filters/conditionals, suppress errors, or accept empty discovery, unexpected skipped/focused tests, missing required reports, or an unmet selected coverage target.

Full verification includes the project's canonical formatting/lint/type/build/public-behavior tests as applicable and its approved coverage policy under [specification section 5.1](DELIVERY-SYSTEM-SPEC.md#51-agree-on-coverage-before-writing-tests). Resolve that choice before configuring a numerical gate: behavior coverage with risk review always applies, and line, statement, branch, or combined targets apply only when selected. Lines and statements are different metrics; 100% is a valid explicit target. Record the approved tool/command, exact threshold, runtime/package/platform scope, aggregation, exclusions, and reporting limits in the project record. Preserve an existing gate until a separately reviewed owner-approved policy amendment and authorized infrastructure changes reconcile it.

Unless an explicitly approved scope says otherwise, selected measurement covers instrumentable owned runtime globally and per package on each required platform, including never-imported files and applicable subprocess/server/browser code. Combine all required shards per platform/package; never union platforms to hide a gap. Inspect exact values and document narrow exclusions and unsupported measurement. Missing or unsupported required measurement blocks the selected gate; an unselected metric is advisory and cannot fail acceptance solely on a percentage. Retain useful failures and required reports as ordinary Actions artifacts. CI cannot replace the independent behavior/risk audit or justify new rejection rules merely to cover a branch; classify findings under [section 5.2](DELIVERY-SYSTEM-SPEC.md#52-classify-coverage-findings-before-correction).

Record tested head/candidate, base/integration state, test revision, canonical command, dependency-lock identity, relevant environment/platform/tool versions, exact result/coverage, and limits. Fingerprint material ignored/untracked inputs. For Git-derived versions, record commit/tag/dirty/build inputs and resolved artifact version with build/install evidence. PR head, synthetic test-merge, and actual merge/squash/rebase identities can produce different artifacts despite equal source trees. Changed head/base/dependency/check/environment/version invalidates affected checks and review; tree equality alone cannot restore build/install claims.

Pin third-party actions/dependencies, grant only necessary CI permissions, and keep production secrets out of tests. Do not run untrusted fork code with privileged credentials. Initial workflows/test infrastructure are authorized setup; later dependency/lint/workflow/shard/helper changes need separately scoped infrastructure maintenance and fresh independent review preserving settled gates. Changed execution authority or permissions stops a bounded worker pending explicit owner approval of the identified high-risk contract, route, named infrastructure/settings ownership, checks, and budget. For infrastructure-only high risk, fresh root blind A/B precede a fresh root infrastructure author using the existing `implement-task` in `infrastructure author` mode, then fresh root D. That author owns only named infrastructure/settings; A/B own tests and policy uses separate independent review. Product C cannot edit restricted infrastructure/settings. Mixed work uses separate fresh product C and infrastructure author sessions; A/B and D cover all behavior/authority and D inherits neither author conversation. An infrastructure repair needs a fresh root infrastructure author and fresh D within the existing task-wide default single repair; no author continuation exception applies to that mode.

## Owner: configure and verify the target branch

Use native branch protection/rulesets on the actual target branch. Availability depends on repository visibility, account plan, and permissions; see [GitHub's protected-branch documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

1. Require PRs and all actual canonical check jobs or a complete fail-closed aggregate. Run an authorized workflow if necessary to expose its real check names. Select the intended trusted check source where supported and require the approved current-base/integration strategy.
2. Disallow ordinary force pushes, branch deletion, and bypass; apply controls to administrators where supported. Inspect all applicable bypass actors/settings. Do not invent reviewer accounts or an approval count a solo owner cannot satisfy: independent agent review is documented evidence, not proven by GitHub identity.
3. Verify the effective active rules and check behavior. If a separately authorized setup plan includes a temporary negative-control PR solely to test native protection, prove that an ordinary merge is blocked, then restore/close the control as planned. This control is setup evidence, not a product submission; known applicable product failures still block submission. Do not force-push or delete the real target branch. No claim of effective enforcement follows from configuration text or a green PR alone.

GitHub accepts successful, skipped, or neutral required-check conclusions. Validation must actually run; an aggregate must reject every failed/cancelled/skipped/neutral/absent/incomplete required platform, shard, and report. Validate the aggregate's dependencies and completeness, including paths/conditions that could omit a result and whether recovery/verification jobs actually run after a failed or skipped ancestor. Native enforcement can still permit bypasses. Record effective rules, trusted sources, base requirements, bypasses, required check names, observed evidence, and limitations in setup notes. Missing or ineffective controls remain gaps; manual owner review is weaker operating evidence, not equivalent enforcement.

Inspect both branch protection and active rulesets, including target refs and bypass actors. An unavailable legacy protection response does not establish that a branch has no effective ruleset. Verify current controls rather than relying on a green check or an older task note.

## Submission gates and the optional pilot

The default remains full canonical local verification of the exact submission candidate plus every required CI platform. Focused local checks guide repairs; they do not replace the full local submission gate. Known applicable failures block submission until classified repair and relevant local checks establish that their cause is addressed. Failed attempts stay recorded; no route permits ignored failures or a merge before proof.

A CI-authoritative route needs a separately approved identified policy change and bounded pilot contract. It is available only for eligible settled mechanical/conventional lower-tier tasks after read-only verification of effective native controls, trusted sources, current-base/integration/bypass settings, and exact candidate/artifact proof. Unknown or ineffective controls block it; configure missing controls only through separately authorized setup. High risk, uncertain evidence, and edits to the pilot's own gates, discovery/coverage, build/release proof, protections, or authority are initially excluded. A small diff cannot approve its own gate.

The approved pilot permits submission after focused public-behavior tests and inexpensive local checks while the full local suite is unexecuted. A waiting PR is unverified and never ready. Full canonical CI on every required platform/package meeting the approved coverage policy, plus fresh independent review of that final candidate/evidence, precedes readiness and an explicit owner merge. If the integration/version strategy cannot establish the required exact artifact/candidate proof before merge, defer eligibility. Candidate/base/check/environment/version changes renew affected checks/review. Failure in full CI stops readiness, routes within existing budgets/allowances, and requires the approved local repair gate and renewed full CI for an update. Revert to full local gating if prerequisites lapse. Neither these settings nor the pilot delegates merge or release authority.

## Protection limits

Tests and workflows remain beside product code. Role blindness, file ownership, approval, and append-only lessons are instructions; native checks cannot prove compliance. Required checks run submitted configuration, so reviewers must inspect infrastructure changes and preserved authority. A changed/deleted workflow or ignored instruction can defeat the process. Do not claim tamper-proof delivery.

First high-risk tests may intentionally fail before implementation on the task branch; known-failing product submission candidates remain blocked. The separately authorized temporary setup control above exists solely to test protection. Policy changes require explicit patch approval and independent policy review before activation. No local hook, cached receipt, or branch rule removes the approved coverage obligations, reviewer obligation, or owner's merge/release authority.
